# 코드는 그대로인데 모델이 바뀐다

*Machine Learning Platform Engineering 스터디 1주차 정리 (CH1~CH3)*

---

1주차 범위는 세 장이다. 1장은 머신러닝 수명주기와 이 책이 만들 플랫폼의 전체 그림, 2장은 MLOps가 DevOps와 어디서 갈라지는지, 3장은 Docker·Kubernetes·CI/CD·Prometheus로 FastAPI 앱 하나(`hello-joker`)를 배포하는 실습이다.

읽는 순서대로 정리하다가 2장과 3장이 서로 안 맞는 지점이 하나 보였다. 2장은 "모델은 코드 변경 없이도 바뀐다"를 MLOps가 DevOps와 다른 이유로 든다. 그런데 3장에서 만드는 파이프라인은 git push가 있어야만 돈다. 이 글은 그 간극을 중심으로 정리했다.

## 1장: 수명주기와 플랫폼 구성

책은 수명주기를 두 단계로 나눈다.

- 실험 단계: 문제 정의 → 데이터 수집·준비 → 데이터 버전 관리 → 모델 훈련 → 평가 → 검증. 화살표는 한 방향으로 그려져 있지만 실제로는 어느 단계에서든 앞으로 되돌아간다
- 개발/스테이징/프로덕션 단계: 같은 단계를 완전히 자동화하고 끝에 배포와 모니터링을 붙인다. 트리거는 CI나 프로그램 호출이고, 지표가 임계값 아래로 떨어지면 다시 트리거된다

플랫폼은 Kubernetes 위에 Kubeflow를 깔고 시작해서 부족한 부분을 하나씩 붙이는 방식이다.

| 역할 | 책에서 쓰는 도구 | 다루는 장 |
|---|---|---|
| 파이프라인 오케스트레이션 | Kubeflow Pipelines | 5장 |
| 피처 스토어 | Feast | 4장 |
| 실험 추적·모델 레지스트리 | MLflow | 4장 |
| 모델 서빙 | BentoML (+Yatai) | 6장, 10장 |
| 드리프트 탐지 | Evidently | 6장 |
| LLM 관측 | Langfuse | 12~13장 |

Kubeflow에 피처 스토어가 기본으로 없어서 Feast를 붙인다는 대목처럼, 도구 하나로 끝내지 않고 조립한다는 전제가 책 전체에 깔려 있다. 저자들도 권장 도구는 출발점이고 며칠짜리 PoC로 직접 확인하라고 쓴다.

실습 프로젝트는 세 개다. 데이터 모달리티가 전부 다르게 골라져 있다.

- 신분증 탐지(이미지): MIDV-500(문서 50종 × 영상 10편 = 500편)과 합성 데이터로 YOLOv8 파인튜닝. COCO 클래스에 신분증이 없어서 파인튜닝이 필요하다
- 영화 추천(표 데이터): MovieLens 1M(약 6천 명이 약 4천 편에 남긴 평점 100만 건). 데이터를 조각으로 나눠 "운영 중에 데이터가 계속 들어오는 상황"을 흉내 낸다
- 사내 문서 RAG(텍스트): DakkaBot. 같은 MLOps 기반 위에 벡터 DB, 가드레일, 비용 최적화를 얹는다

## 2장: 폐쇄 루프와 DevOps와의 차이

2장은 ML 프로젝트를 한 번 만들고 끝나는 게 아니라 계속 도는 루프로 보라고 한다. 문제 정의 → 데이터 수집 → EDA → 모델링·훈련 → 평가 → 배포 → 모니터링 → 유지보수, 그리고 다시 데이터 수집으로.

기억해 둘 만한 부분만 추리면 이렇다.

- 문제 정의 단계의 질문 목록을 이해관계자별로 나눠놨다. 비즈니스(잘못된 예측의 비용, 허용 오차), 기술(데이터 위치, 재훈련을 촉발할 지표), 법무(민감 정보, 데이터 거버넌스). "고객 이탈률을 예측하라" 수준의 요구로는 평가 기준을 뽑을 수 없다는 예시가 붙어 있다
- 데이터 수집에서 가장 자주 빠뜨리는 게 리니지라고 짚는다. 리니지가 있으면 잘못된 데이터셋을 쿼리 한 번으로 다시 만들고, 없으면 추출 스크립트를 다시 짜야 한다
- 모델(가중치+네트워크)과 코드(아키텍처+지원 코드)는 따로 버전이 움직인다. 코드는 그대로인데 재훈련으로 모델만 바뀌는 경우가 흔하다
- 평가 지표는 도메인 요구에서 나온다. 의료는 위양성을 줄이려 정밀도를, 금융 사기는 놓치는 비용 때문에 재현율을 본다. 홀드아웃 데이터셋도 훈련 데이터만큼 버전과 리니지를 관리해야 하고, 분할이 바뀌면 이전 평가 점수는 버려야 한다

DevOps와의 차이는 여섯 가지로 정리돼 있는데, 결국 세 개로 묶인다.

1. 데이터가 1급 구성요소다. DevOps는 데이터 수명주기를 이 정도로 관리하지 않는다
2. 코드 변경 없이도 모델이 바뀐다. 그래서 CI/CD 위에 지속적 훈련(CT)이 붙는다
3. 빌드가 아니라 실험을 추적해야 한다

성숙도는 구글의 MLOps 레벨을 그대로 가져온다.

| 레벨 | 배포하는 것 | 특징 |
|---|---|---|
| 0 | 모델 | 수동 스크립트, 모니터링 없음, 릴리스 드묾 |
| 1 | 재훈련 파이프라인 | 새 데이터로 자동 재훈련(CT), 개발·운영이 같은 파이프라인 사용 |
| 2 | 파이프라인을 만드는 파이프라인 | 파이프라인 컴포넌트 자체의 빌드·테스트·배포를 CI/CD로 자동화 |

레벨 0에서 1로 넘어갈 때 배포 대상이 "모델"에서 "모델을 만드는 파이프라인"으로 바뀐다는 점이 핵심이다.

## 3장: hello-joker를 클러스터에 올리기

3장은 ML 이야기가 거의 없다. 무작위 농담을 돌려주는 FastAPI 앱을 이미지로 만들고, K8s에 올리고, CI/CD로 자동화하고, 지표를 붙인다.

스터디에서는 교재 환경을 그대로 쓰지 않고 몇 군데를 바꿨다.

| 교재 | 스터디 | 이유 |
|---|---|---|
| `python:3.10-slim-buster` | `python:3.10-slim-bookworm` | buster가 EOL이라 `apt-get update`가 404로 실패 |
| GitLab + GitLab Runner | Gitea + Gitea Actions(act_runner, dind) | 로컬 클러스터에 설치형으로 |
| Docker Hub | 그대로 (Harbor는 도전과제) | |
| K8s 1.24 | K3s 1.29 / kind | Gitea Runner 최소 지원 버전 |

순서는 이렇다.

1. Docker: 이미지 빌드, 로컬 실행, 레지스트리 푸시. 태그는 버전이나 커밋 ID
2. K8s 객체: Pod → ReplicaSet → Deployment. Deployment에서 이미지 태그를 바꾸면 새 ReplicaSet이 생기면서 롤링 업데이트되고, `rollout undo`로 되돌린다
3. Service: NodePort, ClusterIP, LoadBalancer. K3s는 klipper-lb가 노드 IP를 LB 외부 IP로 내준다
4. Helm: `helm create`로 차트를 만들고 `values.yaml`의 이미지 저장소·태그·레플리카 수를 바꿔 배포
5. CI: `test`(pytest) → `build`(이미지를 커밋 SHA 8자리 태그로 빌드·푸시) → `update`(yq로 차트의 `image.tag`를 그 SHA로 바꾸고 저장소에 다시 커밋·푸시)
6. CD: Argo CD가 저장소의 Helm 차트를 보고 클러스터를 맞춘다(`selfHeal: true`). 저장소가 유일한 진실의 원천이다
7. 모니터링: `starlette_exporter`로 `/metrics`를 열고, 파드 어노테이션(`prometheus.io/scrape`)으로 Prometheus가 긁어 가게 한 뒤 Grafana로 본다

5번과 6번을 합치면 흐름이 된다. 개발자는 코드만 푸시하고, CI가 이미지를 만들고 차트의 태그를 갱신하고, Argo CD가 그 변경을 보고 배포한다. 사람이 `kubectl apply`를 칠 일이 없다.

## 이 파이프라인에는 모델이 들어갈 자리가 없다

3장 파이프라인을 2장의 성숙도 표에 대보면 레벨 0과 1 사이 어딘가가 아니라, 애초에 축이 다르다.

트리거가 `on: push` 하나다. 무언가가 바뀌었다고 알리는 신호는 git 커밋뿐이고, 배포 단위의 식별자도 커밋 SHA로 만든 이미지 태그 하나다. 그 태그가 가리키는 건 코드 버전이다.

2장의 주장을 이 구조에 넣어 보면 막힌다.

- 재훈련으로 모델만 바뀌었다. 코드 커밋이 없으니 CI가 돌지 않는다. 이미지 태그도 안 바뀌니 Argo CD도 할 일이 없다
- 모델 가중치를 이미지 안에 굽는다고 해보자. 그러면 모델이 바뀔 때마다 의미 없는 커밋을 만들어 CI를 깨워야 한다. 태그는 여전히 코드 SHA라서, 같은 태그 아래 다른 모델이 들어가는 일도 생긴다
- 데이터 드리프트가 감지됐다. 이걸 받아줄 트리거가 없다

리니지 쪽에서 보면 문제가 더 분명하다. 2장은 운영 중인 모델에서 출발해 "어떤 데이터, 어떤 코드, 어떤 설정으로 만들었나"를 거꾸로 따라갈 수 있어야 한다고 했다. 3장 구조에서 운영 중인 파드에서 따라갈 수 있는 건 이미지 태그 → 커밋까지다. 데이터 버전과 하이퍼파라미터는 어디에도 기록되지 않는다.

이건 3장의 결함이라기보다 3장이 DevOps 장이기 때문이다. 책도 3장 도구들이 "ML에 특화된 건 아니다"라고 먼저 말한다. 오히려 뒤에 나올 도구들이 정확히 이 빈칸에 맞춰져 있다는 게 보인다.

| 빈칸 | 채우는 도구 |
|---|---|
| 모델 버전과 코드 버전을 분리해서 기록 | MLflow 모델 레지스트리 |
| 데이터·피처 버전, 시점 기준 조회 | Feast |
| 코드 푸시 말고 다른 트리거(일정, 지표)로 재훈련 | Kubeflow Pipelines |
| 드리프트를 감지해 재훈련을 깨움 | Evidently |

그래서 3장은 "배포 자동화의 바닥"을 까는 장으로 읽는 게 맞다고 본다. 1장 그림 1.9(코드 변경 → 이미지 빌드 → 매니페스트 갱신 → 배포)가 바로 이 3장 파이프라인이고, 1장 그림 1.2에서 말한 "지표가 떨어지면 다시 트리거"는 아직 없다.

## CI가 자기 저장소에 푸시할 때

3장 CI에서 하나 더 걸린 게 있다. `update` 잡이 차트를 고쳐서 `main`에 다시 푸시한다. 그런데 워크플로 트리거도 `main` 푸시다. 그대로 두면 CI가 자기 커밋으로 자기를 다시 깨운다.

교재는 커밋 메시지에 `[skip ci]`를 넣어서 막는다. Gitea Actions로 옮기면 무엇이 이걸 막는지 따로 확인했다.

워크플로가 카운터 파일을 1 올리고 `main`에 푸시하게 만들고, 카운터가 3이 되면 멈추게 했다. 케이스는 "누구 권한으로 푸시하나"(워크플로 기본 토큰 / 개인 액세스 토큰) × "커밋 메시지에 `[skip ci]`가 있나" 네 가지. 생성된 run 수를 셌다. Gitea 28.2.0, act_runner 0.6.1.

| 푸시 권한 | 메시지 | 워크플로가 한 푸시 | 생성된 run | 결과 |
|---|---|---|---|---|
| 기본 토큰 | `[skip ci] bump N` | 1 | 1 | 재트리거 없음 |
| 기본 토큰 | `bump N` | 1 | 1 | 재트리거 없음 |
| 개인 토큰(PAT) | `bump N` | 3 | 4 | 루프. 안전장치에서 멈춤 |
| 개인 토큰(PAT) | `[skip ci] bump N` | 1 | 1 | 재트리거 없음 |

run 1개는 워크플로 파일을 처음 푸시할 때 생긴 것이다.

막는 장치가 두 개였다.

첫째, 기본 토큰으로 푸시하면 푸시 주체가 `gitea-actions` 봇(내부 user id -2)으로 기록된다. Gitea는 이 봇이 만든 이벤트로는 워크플로를 띄우지 않는다. `services/actions/notifier_helper.go`의 `notify()`에 `Doer.ID == ActionsUserID`면 무시하는 분기가 있고 주석이 "avoiding triggering cyclically"다. 설정으로 끌 수 없다. GitHub Actions의 `GITHUB_TOKEN`과 같은 동작이다.

둘째, `[skip ci]`는 `[actions] SKIP_WORKFLOW_STRINGS` 설정값이다. 기본 목록은 `[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]`, `[actions skip]`이고, 푸시의 head 커밋 메시지에 부분 문자열로 들어 있으면 건너뛴다. 이 목록을 `[noloop]`로 바꿔서 Gitea를 다시 띄우자 PAT + `[skip ci]` 케이스가 루프를 돌았다. 그러니까 이 방어선은 서버 설정에 묶여 있다.

정리하면 스터디 워크플로(`actions/checkout` 기본 토큰으로 푸시)는 `[skip ci]`를 빼도 루프가 안 돈다. 교재의 GitLab 버전은 `GITLAB_ACCESS_TOKEN`이라는 별도 토큰으로 클론·푸시하니 PAT 케이스에 해당하고, 거기서는 `[skip ci]`가 실제로 일을 한다.

운영으로 가져갈 때 주의할 점은 기본 토큰이 아니라 봇 계정 PAT나 배포 키로 바꾸는 순간이다. 다른 저장소를 건드리거나 브랜치 보호를 우회하려고 흔히 바꾸는데, 그때 봇 차단이 사라지고 `[skip ci]` 문자열 하나와 그 서버의 설정값만 남는다. 트리거를 `paths-ignore: ['hello-joker/values.yaml']`처럼 경로로 거는 편이 메시지 규칙보다 의도가 분명해 보인다(이건 직접 재보지는 않았다).

검사 대상이 head 커밋 하나라는 것도 소스에서 확인했다. 여러 커밋을 한 번에 푸시하면 중간 커밋의 `[skip ci]`는 안 먹힐 것으로 보이는데, 이건 소스만 읽었고 실측하지 않았다.

<details>
<summary>실험에 쓴 워크플로 (PAT + 일반 메시지 케이스)</summary>

```yaml
name: loop-test
on:
  push:
    branches: [main]
permissions:
  contents: write
jobs:
  bump:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          token: ${{ secrets.LOOP_PAT }}   # 기본 토큰 케이스는 ${{ github.token }}
      - name: bump counter and push
        run: |
          N=$(cat counter.txt)
          if [ "$N" -ge 3 ]; then echo "safety stop at $N"; exit 0; fi
          N=$((N+1)); echo $N > counter.txt
          git config user.name loop-bot; git config user.email loop-bot@example.com
          git commit -am "bump $N"          # skip 케이스는 "[skip ci] bump $N"
          git push origin HEAD:main
```
